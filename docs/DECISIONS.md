# Decisions

Format: **Decision**: reason. *Alternatives considered.*

- **`ParserEvent` discriminates on `type`, and the artifact's declared MIME type is named `artifactType`** (§5 lists `artifact_open {identifier, type, title, language?}`): a TS discriminated union cannot carry two `type` properties, and `type` is already the discriminator on every other event, matching `StreamEvent` in `packages/shared`. The artifact's `type` attribute (e.g. `application/vnd.react`) is therefore exposed as `artifactType` and preserved verbatim. *Naming the MIME field `type` with a `kind`/`event` discriminator (breaks consistency with `StreamEvent`); dropping the discriminator.*
- **Fence language is the first whitespace-delimited word of the info string, lowercased** (e.g. `` ```mermaid extra `` → `mermaid`): follows CommonMark's info-string convention where the first word is the language and the rest is ignored. *Comparing the whole info string to `mermaid` (a fence like `` ```mermaid lang `` would then not render as a diagram).*

- **Local Hono server + Vite React UI instead of Next.js**: the app needs long-lived processes (shell execution, streaming, SQLite) on the user's machine; a local server makes that explicit, and the UI stays a plain client. *Next.js with a custom server.*
- **Sandboxed iframe with vendored libraries instead of Sandpack's hosted bundler**: works offline and never sends user code to a third party. *Sandpack, a self-hosted bundler.*
- **Code-first build path in Impeccable**: the run is unattended and has no image generation. *Comp-first.*
- **Jev commit-review agent (`jev-reviewer`)**: reviews git commits with Jev (TypeSafe's System One model) via `scripts/jev-review.mjs`, one TypeSafe request per commit carrying typed judgments (category, quality, security/bug/test risk, blocking). Chose direct HTTP (`fetch`) over `@typesafe-ai/sdk` so the script stays dependency-free and runs with `node` alone. *Using the official JS SDK; having Jev write free-form prose.*
- **Jev reviewer runs in a `pre-push` git hook (`.githooks/pre-push`, enabled via `core.hooksPath .githooks`)**: reviews commits about to be pushed and blocks when Jev flags `blocking` or `risk_security` >= 0.6. Fails **open** on a missing key or transient error so devs are never blocked silently; bypass with `JEV_REVIEW_BYPASS=1` or `git push --no-verify`. *`pre-commit` (can't review a not-yet-created commit) and `commit-msg` (message-only).*
- **One branch per feature, one commit per task, OpenSpec for both**: each §12 step is a *feature* worked on branch `feature/N-<slug>` and planned as OpenSpec change `N-<slug>` (via `openspec-propose`); each `tasks.md` item is a *task* implemented with `openspec-apply-change` and committed as `feat(N-<slug>): <summary>`; a feature is finished with `openspec-archive-change` then merged to `main`. This gives a reviewable branch per feature and a bisectable commit per task. *A single `main` branch with one commit per step (no feature isolation); OpenSpec changes without git branches (plan and code diverge from history).*
- **`packages/core` gains `@types/node` and `types: ["node"]`, and `@openartifact/shared` exposes its TypeScript source as its package entry (`main`/`types`/`exports` → `./src/index.ts`)**: the adapters need Node 20+ globals (`fetch`, `AbortSignal`, `setTimeout` for backoff) and the shared package is source-only (no build emit), so cross-package imports resolve the `.ts` source directly — the standard pnpm "internal package" pattern with `moduleResolution: Bundler`. *Building shared to `.d.ts` (extra build step, drift risk); typing `fetch`/`AbortSignal` by hand (duplicates @types/node).*
- **TypeScript pinned to 5.9.3, not the `latest` 7.0.x**: `typescript-eslint` 8.70.1 declares a peer range of `<6.1.0`, so the newly-released TS 7 (native compiler) breaks type-aware linting. Pin an exact, widely-supported 5.x until `typescript-eslint` supports TS 7. *TS 7.0.2 `latest`; an older 5.x (more drift).*
- **Tailwind CSS 3.4 (not v4)**: §7 requires design tokens as CSS variables consumed "from the Tailwind config", which maps to v3's `theme.extend` + `tailwind.config.js`. v4's `@theme`/CSS-first model would change how later steps implement tokens. *Tailwind v4.3.*
- **Vite 7 + React 18.3 + `@vitejs/plugin-react` 5**: spec pins React 18 (§2); Vite 7 is the stable major that supports Node 22, and plugin-react 5 declares `vite ^7 || ^8`. All versions pinned exactly. *Vite 8 (brand new); React 19 (spec says 18).*
- **Server default port `4318` (overridable via `PORT`)**: the spec does not pin a port, and common ones (3000/8080) collide with other dev tools. 4318 is arbitrary but unlikely to clash; recorded here so later steps and the e2e webServer reuse it. *Port 3000, 8080.*
- **Server runs via `tsx watch` in dev and compiled ESM (`tsc -p tsconfig.build.json` → `node dist/index.js`) in production**: `tsx` gives instant restart during development, while a real `tsc` emit keeps `start` free of a dev-only dependency. The server tsconfig uses `module`/`moduleResolution: NodeNext` with `.js` relative imports so the emitted code runs on Node without a bundler. Tests are excluded from the emit so `vitest` never picks up `dist/*.test.js`. *Run everything through tsx; a bundler-based build.*
- **Dev vs prod serving split by `NODE_ENV`**: the server serves the built web app (`apps/web/dist`) when `NODE_ENV=production` and the build exists, otherwise proxies every request to the Vite dev server at `127.0.0.1:5173` (with a 502 if Vite is not up). This matches the design's intent and keeps `pnpm dev` a single command. *Always serve dist; always proxy.*
- **`@types/node` pinned to 22.x, not the 26.x `latest`**: the runtime is Node 22 (`.nvmrc`), so type defs should match the runtime to avoid APIs that do not exist there. *@types/node 26.6.3.*
- **`withRetry` `maxAttempts` means total attempts (default 3 ⇒ up to 2 retries)**: the task text and design.md both say "max 3 attempts", while SPEC §4 says "retry ... at most 3 times" (≤3 retries). 2 retries satisfies both readings ("at most 3 times" is an upper bound), and total-attempts is the less surprising semantic for a named `maxAttempts` option. *4 total attempts (3 retries); a separate `maxRetries` option (ambiguous naming).*
- **Equal jitter (`delay = exp/2 + rand*exp/2`) rather than full jitter (`rand*exp`)**: guarantees a positive delay so the first retry can never be a zero-ms hammer; still bounded and jittered. *Full jitter; "decorrelated" jitter (needs extra state).*
- **`Retry-After` overrides backoff exactly (no added jitter)**: it is an explicit server directive, so `withRetry` sleeps the parsed delay as-is; `ProviderHttpError.retryAfterMs` carries the already-parsed value and `parseRetryAfter` converts seconds/HTTP-date headers. *Adding jitter to `Retry-After` (ignores the server's own pacing).*

- **`withFallbackTools` re-serializes non-tool parser events (artifact open/delta/close, mermaid open/delta/close) back into literal `text_delta` events** rather than dropping them: the canonical `StreamEvent` union has no artifact/mermaid event types, and the UI (feature 6/7) parses artifacts and diagrams from the assistant text itself, so the fallback decorator must not consume that content. Only the `<tool_call>` blocks are extracted; everything else is re-emitted as text (an incomplete artifact is left without a closing tag so the downstream parser flags it `incomplete` too). *Dropping artifact/mermaid events (loses content); adding artifact/mermaid types to the canonical `StreamEvent` (changes the shared model mid-feature).*
- **Fallback tool-call ids are `call_<n>`, a per-stream counter**: the `<tool_call>` protocol has no native id, and a counter is deterministic for tests while remaining unique within a single turn (the agent loop correlates tool results per turn). *Random ids (non-deterministic tests); a global counter (state leaking across streams).*
- **Anthropic `max_tokens` defaults to 4096 when a `ChatRequest` omits it**: the Messages API requires `max_tokens` on every request, but the canonical `ChatRequest.maxTokens` is optional. A generous default keeps adapters callable without forcing every caller to set a cap. *Making `maxTokens` required on `ChatRequest` (couples the neutral contract to one vendor); sending no `max_tokens` (Anthropic rejects the request).*
- **Anthropic tool results are grouped into one `user` message (all consecutive `tool`-role results flushed before the next non-tool message)**: the Messages API requires `tool_result` blocks to live inside a `user` message, and grouping consecutive results into a single user message avoids a run of near-empty user messages. *One user message per tool result (noisier history); appending results to the preceding assistant message (Anthropic rejects tool results on an assistant turn).*
- **Gemini `functionResponse.name` is recovered from a call-id→name map built from prior assistant `tool_call` parts, falling back to the call id**: the canonical `tool_result` part only carries `callId`, but Gemini correlates a `functionResponse` with its `functionCall` by function name, so `buildGeminiRequest` scans earlier assistant turns to recover the name. *Always using `callId` as the name (Gemini sees a bogus function name); adding a `name` field to `tool_result` (changes the shared model mid-feature).*
- **Gemini tool-call ids are `call.id` when present, else a synthesized `call_<n>` per-stream counter**: Gemini's `functionCall` only carries an `id` on newer API versions, but the canonical `tool_call_start`/`tool_call_end` events require an id; the counter is deterministic for tests and unique within a turn, mirroring the fallback-parser convention. *A random id (non-deterministic tests); dropping the id (breaks downstream correlation).*
- **Gemini `finishReason` maps only `MAX_TOKENS` → `max_tokens`, everything else (including `STOP`) → `end_turn`**: Gemini has no distinct tool-call finish reason — a model that emits a `functionCall` still finishes with `STOP` — so a tool call surfaces through the parts, not the stop reason. *Mapping a hypothetical tool reason (no such value exists in the Gemini enum).*
- **Ollama tool results are sent as `role:"tool"` messages with a `tool_name` recovered from a call-id→name map (falling back to the call id)**: Ollama's `/api/chat` correlates a tool result with its call by `tool_name`, not by id, and Ollama assigns no id to native tool calls — so `buildOllamaRequest` recovers the name the same way `buildGeminiRequest` does, and streamed calls get a synthesized `call_<n>` id. *Adding a `name` field to `tool_result` (changes the shared model mid-feature); matching by position (fragile when results arrive out of order).*
- **Ollama tool-call arguments are treated as a complete JSON object (never a fragment string), with string/`null` normalized defensively**: in native mode Ollama streams `tool_calls[].function.arguments` already parsed, unlike OpenAI's incremental fragments, so the reducer emits `tool_call_start`/`tool_call_end` in one step per call and skips `tool_call_delta`. *Emitting a synthetic `tool_call_delta` per call (misrepresents the wire format and adds noise for consumers).*
- **`scripts/smoke.mjs` reuses the real `createProviderAdapter` (importing `packages/core` TS source) and is run with `tsx`, added as a root devDependency**: the smoke test exercises the exact adapter/retry code path a real request takes, rather than a hand-rolled parallel HTTP client; `tsx` resolves the source-only workspace packages (which use extensionless imports and `.ts` package entries) with no build step. *A raw-HTTP smoke script (duplicates adapter logic, drifts); a `tsc` build of core/shared just for smoke (extra emit + config).*
- **The Gemini smoke path uses the adapter's hand-rolled REST streaming, not `@google/genai`**: `design.md`'s original smoke note assumed the official client, but the shipped `gemini.ts` adapter already speaks `:streamGenerateContent?alt=sse` directly, so no `@google/genai` dependency or dynamic import is needed. *Adding `@google/genai` (dead weight; two Gemini implementations to keep in sync).*
- **`pnpm smoke` skips exit 0, real errors exit 1, and `--provider all` runs every provider**: a missing key is an unconfigured environment, not a failure, so CI-unfriendly exit codes are avoided while a genuine request error still fails loudly. Output is limited to provider id, model, reply text and usage tokens; the key is never rendered. *Exit 2 on skip (confuses "not configured" with "broken"); silently passing a failed request.*
- **Per-provider smoke defaults live in a registry in `scripts/smoke.mjs` and are overridable with `--model`/`--base-url` or `SMOKE_<ID>_MODEL`/`SMOKE_<ID>_BASE_URL`**: the adapter layer itself must stay provider-name-agnostic (capability flags only), but the smoke CLI is a configuration surface, so it may name providers; env overrides let one script target OpenAI, Groq, OpenRouter, vLLM, LM Studio, etc. through the single `openai-compatible` adapter. *Hard-coding only OpenAI's endpoint (can't smoke the other compatible vendors); encoding base URLs in `.env` under new keys.*
- **Path jail resolves a not-yet-created target by realpath-ing its longest existing ancestor and re-appending the missing suffix** (`realpathExistingPrefix`): `write_file` must validate a path that does not exist yet, and `fs.realpath` throws on it; walking up to the nearest existing ancestor still resolves every symlink in the chain, so a future file created through a symlinked directory that escapes the workspace is rejected. *Requiring the target to already exist (breaks `write_file`); skipping symlink resolution for missing targets (a symlinked ancestor could escape).*
- **`isSecretPath` interprets `.env*` literally as any basename starting with `.env`**: §9 lists `.env*` alongside `*.pem`/`*.key`/`id_rsa*`, so the glob's literal reading (which also matches `.env.local`, `.env.template`, …) is followed; false positives only cost an approval, while false negatives could leak a secret to a provider. *Excluding `.env.template`/`.env.example` by hand (unsafe: a provider key could live in any `.env*` file).*
- **Read tools return errors as `ToolResult { isError: true }` rather than throwing, with path-jail violations included**: the agent loop then has a single path for tool failures (every `tool_call` gets a `tool_result`, so a rejected read still closes the history cleanly). `read_file` reports missing paths and directories as those error results too. *Throwing `PathJailError`/`Error` from `execute` (the loop would need a second error path).*
- **`read_file` line numbers use a right-padded `N|content` prefix, `list_directory` defaults to depth 3 (max 20) and renders an indented tree (directories first, trailing `/`, symlinks `@`, never followed)**: the padded prefix keeps columns aligned for multi-digit line counts, and a bounded depth prevents a runaway listing of huge trees; symlinks are listed but not followed so the jail can't be escaped through a link. *`N: content` (ambiguous with code); no depth cap (unbounded output).*
- **`glob` returns sorted relative *file* paths only, skips `.git/`, never follows symlinks, and caps at 500 matches; `search_code` caps at 100 matches**: §8 says glob finds *files*, so directories are not returned even when a pattern names one; sorting makes output deterministic for tests and diffing; caps bound both work and token cost. *Returning directories too; preserving walk order; no cap.*
- **`search_code` locates ripgrep via a new `ToolContext.findRipgrep()` hook (undefined → JS fallback) and falls back to the JS walk if spawning rg fails**: the design.md planned a `findRipgrep` option; an injected resolver keeps tests deterministic (a fake `rg` script) and avoids probing `PATH` at runtime. Both paths respect `.gitignore`, include hidden files, and skip `.git/`, so results stay consistent regardless of which engine runs. *Hard-coding an `rg` spawn (non-deterministic tests, fails in CI without ripgrep); JS-fallback-only (loses rg's speed).*
- **The `.gitignore` matcher implements a common subset (blank/`#` lines, `!` negation, trailing `/` directory-only, leading `/` anchoring, `*`/`**`/`?`) with each rule scoped to its `.gitignore` directory and deeper rules overriding shallower ones**: that covers the patterns a coding agent actually generates and matches git's precedence closely enough for a tree listing, without pulling a dependency. Parent `.gitignore` files between the workspace root and a listing root are not applied (a documented simplification). *A full gitignore implementation or `ignore` dependency (heavier, more surface); ignoring `.gitignore` entirely (breaks a core §8 requirement).*
- **Snapshots are written as `<snapshotRoot>/<conversation>/<turn>/<counter>_<basename>.before`, with the per-turn counter derived by listing the directory for the largest `N_` prefix**: design.md fixes the path; a directory-derived counter keeps successive mutations within one turn ordered without module-level state that would leak across turns or processes. `snapshotFile` returns `undefined` for a not-yet-existing path (nothing to snapshot) and `snapshotBeforeMutation` honors both the host `ctx.snapshot` callback and `ctx.snapshotRoot`/`conversationId`/`turnId`. *An in-memory counter (resets per process, races); timestamped names (non-deterministic tests); snapshotting a tombstone for brand-new files (undo of a create is just a delete).*
- **`edit_file` does exact-substring replacement with `String.prototype.replace(needle, () => newString)` for a single match and `split/join` for `replaceAll`**: both avoid `$`-pattern substitution (so a literal `$` in `newString` stays literal) without reaching for regexes. An empty `oldString` is rejected, a missing match reports the path and a one-line preview of `oldString`, and an ambiguous match reports the occurrence count plus (up to five) line numbers; the file is left untouched in both failure cases. *`String.prototype.replaceAll` (fine, but the split/join form reads clearer with a dynamic needle); regex-escaped replacement (needless escaping of `$`/backslashes).*
- **`write_file` snapshots only when the target already exists and creates parent directories with `recursive: true`**: §8 says to snapshot before the agent *changes* a file, and creating a fresh file changes nothing prior; undo of a create is a delete, not a restore. Parent creation matches the "create a file" scenario in §8 and keeps the tool a one-call operation. *Snapshotting a marker for new files; requiring parents to exist.*

- **The approval flow lives in a pure `agent/approval.ts` module (`resolveApproval` + `applyApprovalDecision`), separate from the orchestrating loop**: mode resolution and decision application are deterministic, side-effect-free functions the loop will call, so they can be unit-tested without a fake provider; the async generator (task 4.1) stays thin. `resolveApproval(subject, args, mode, policies)` takes injectable `isSecretPath`/`isSudoCommand` policies defaulting to the real security helpers. *Resolving approval inside the loop generator (untestable without a scripted provider); a class hierarchy of approval strategies (unnecessary ceremony).*
- **`isSudoCommand` matches `sudo` as a standalone word delimited by start/end, whitespace or a shell metacharacter — `/(^|[^\w-])sudo([^\w-]|$)/`**: it must catch `env sudo x` and `echo | sudo tee` but not the prefix `sudoers` or hyphenated words like `not-sudo`; the `\b` word-boundary alone treats `-` as a boundary and would flag `not-sudo`. False positives only cost one approval; false negatives could auto-run a privileged command. *`\bsudo\b` (over-broad); leading-`sudo`-only (misses `env sudo` / pipes).*
- **Cancellation is a pure history-repair helper (`pendingToolCallIds` + `cancelPendingToolCalls`) that appends one `tool` message with `"cancelled by user"` (`isError: true`) results for unanswered calls**: §8 requires every `tool_call` to have a `tool_result` after a cancel, and grouping the synthetic results into a single `tool` message mirrors the Anthropic adapter's consecutive-results convention. The helper never mutates input and returns the array unchanged when nothing is pending, so `pendingToolCallIds(history) === []` is the integration test's validity assertion. *One `tool` message per pending call (noisier); mutating history in place (surprising for a pure layer).*

- **The orchestrating `AgentLoop` (`agent/loop.ts`) was implemented inside task 4.1 rather than a dedicated 3.x task**: the change's tasks built the loop's building blocks (state machine, limits, identical-failure, context, approval, cancellation, system prompt) but named no separate "write the loop" task, and the §12.4 acceptance test (read → edit → execute → answer via a scripted fake provider) cannot run without the loop. The loop is an async generator of `AgentEvent`s (`state`, `text`, `tool_start`, `tool_result`, `approval_request`, `approval_decision`, `done`, `error`) with an injected `ApprovalHandler`, exactly as design.md describes; the integration test is its first consumer. *Deferring the loop to feature 6 (the server would then own it, violating the React/Hono/DOM-free core boundary); a separate 3.4 task (breaks the one-task-per-commit ledger retroactively).*
- **The agent loop compacts context by stubbing old tool results only; turn summarization (the second compaction stage in §8) is not implemented in this feature**: §12.4's acceptance criteria (read → edit → execute → answer, escape rejection, cancel-keeps-history) do not exercise summarization, and it needs an extra model round-trip with its own failure handling. `ContextManager.compact` returns the stubbed history, and the loop leaves it there when still over threshold (history degrades to stubbed form rather than failing). *Implementing summarization now (scope not required by the feature's done-when, more surface to keep green); pretending stubbing is the only compaction stage.*

- **Design tokens are CSS custom properties consumed through Tailwind's `theme.extend` (colors → `var(--color-*)`, type/radius/shadow/motion likewise), with `:root` = dark and `[data-theme="light"]` overriding**: §7 requires tokens as CSS variables consumed "from the Tailwind config", and a single `data-theme` attribute flip must retheme the whole app with no config rebuild; Tailwind v3 (already chosen in an earlier decision) maps semantic names to `var(--…)`, so a color changes in exactly one place and components never hard-code a value. *Two Tailwind configs or pervasive `dark:` variants (harder to verify "no hard-coded colors outside tokens.css"); Tailwind v4 `@theme` (breaks the chosen v3 config model).*
- **Default theme is dark, and `prefers-color-scheme` is deliberately ignored — only a stored `localStorage` preference overrides it**: PRODUCT.md makes dark first-class ("often used in dim rooms") and SPEC §7's scenario requires dark when there is no stored preference. The inline `index.html` bootstrap sets `data-theme` before first paint to avoid a flash. *Honoring `prefers-color-scheme` as the default (contradicts the "default dark" scenario).*
- **UI fonts are IBM Plex Sans (UI) + IBM Plex Mono (code/paths/terminal), self-hosted**: both are SIL OFL (no CDN, no runtime network), pair as a family, and give OpenArtifact a calm, precise developer-tool voice that is distinct from any commercial AI product while staying legible over hours-long sessions. Mono is reserved for code, paths and terminal output only (PRODUCT constraint). *Inter (ubiquitous/featureless); JetBrains Mono (strong code face but a branded name).*
- **Secondary text is tinted from the foreground hue (indigo cast), never pure gray, and the muted tier is checked ≥ 4.5:1 in both themes**: the craft floor bans gray-on-gray, so the neutrals are HSL-tilted toward indigo (hue 222–228) even for "gray" surfaces. *Pure neutral grays (flat, template-like); skipping a contrast check on the muted tier.*
- **UI primitives use an authored SVG icon set (`components/ui/icons.tsx`, 1.5 stroke, `currentColor`) instead of installing `lucide-react` in this feature**: the primitives themselves take any `ReactNode` as an icon, so the icon set is swappable; authoring a few geometric icons (plus, check, x, play, stop, settings-sliders, panel, chevron, terminal, message) keeps `apps/web` offline and dependency-free until the chat/approval surfaces (feature 6) actually need a full library. *Installing lucide-react now (a dependency before any consumer needs it); emoji/unicode glyphs as icons (craft-floor ban).*
- **The `danger` Button variant is an outline→soft-fill style (`border-border text-danger`, hover fills `danger-bg` + `border-danger`), not a solid red button**: the semantic `--color-danger` is a *text* color at 66 % lightness in dark mode, so solid `bg-danger` with white text fails AA contrast; a proper solid destructive button would need a dedicated medium-red surface token plus a themed foreground — speculative while only the primitives exist. The soft style stays AA-compliant in both themes and is the natural fit for "Reject"/"Stop" in feature 6. *Solid `bg-danger` + white text (contrast fails in dark); adding `--color-danger-solid`/`--color-danger-fg` now (no consumer yet).*
- **The shared focus ring is a `.focus-ring` utility in `@layer components` (box-shadow `var(--ring-focus)`) applied to `Button`/`IconButton`, while the base layer keeps the global `:focus-visible` outline for all other focusable elements**: components-layer priority beats base, so primitives get the polished two-layer ring (background gap + accent) and future inputs/links keep the simpler outline — one token, two surfaces, zero per-component CSS. *A single global box-shadow ring (custom widgets like the future `role="separator"` divider lose the outline fallback); per-component `focus-visible:` Tailwind variants everywhere (drift).*
- **The workspace shell uses a JS `useMediaQuery("(min-width: 900px)")` hook (not a CSS breakpoint) to switch the artifact panel between the side-by-side split and the full-screen sheet**: the split pane's left width is an inline `style` (px) driven by the drag divider, which cannot be media-queried in CSS; a single React tree branches on the match so the terminal-log collapse state survives a desktop↔mobile resize. Below 900 px the divider and right pane are unmounted and the sheet is a `role="dialog"` overlay with Escape-to-close. *Two duplicate DOM trees gated by `max-[899px]:` variants (state resets on resize); a resize-panel library (heavier than one divider justifies).*
- **The empty terminal log's placeholder uses `--color-text-secondary`, not `--color-text-faint`**: axe flagged `text-faint` (the disabled tier) at 3.26:1 on `bg-sunken` in dark mode, and the craft floor requires placeholder text ≥ 4.5:1; the disabled tier is reserved for genuinely disabled content. *Keeping `text-faint` (fails AA); introducing a new token (the existing tier already fits).*
- **`execute-command.test.ts` "kills the whole process tree" uses a 1000 ms timeout (was 200 ms)**: under `pnpm check`'s parallel workspace test load, `node parent.js` occasionally could not spawn its grandchild and write `child.pid` before the 200 ms timeout killed the process group, making the test read a file that was never written. 1000 ms is a 5× margin while still asserting a real timeout-kill. *Keeping 200 ms (flaky); polling for `child.pid` in the test (races the tool's own timer).*
- **`e2e/screenshots.spec.ts` resolves `docs/screenshots/` from `process.cwd()`, not `import.meta.url`**: Playwright rewrites `import.meta.url` for its transpiled spec files (the first attempt pointed it at `repos/docs/screenshots/` instead of `repos/kxlaud/docs/screenshots/`), while the root `pnpm screenshots` script always runs with the repo root as the process cwd, so `join(process.cwd(), "docs", "screenshots")` lands the captures reliably. *Anchoring on `import.meta.url` (wrong path under Playwright's loader); a `find-up` from `__dirname` (spec files have no `__dirname` under ESM).*
- **Screenshots live in their own Playwright project (`--project=screenshots`) and `pnpm e2e` targets `--project=e2e`**: §7/design.md make the screenshot script a capture tool, not an assertion, so it must not run under `pnpm check` (slow, environment-dependent); a single config with two projects shares the web-server bootstrap and keeps the axe suite (`smoke.spec.ts`) as the only `pnpm check` e2e assertion. The `e2e` project ignores `screenshots.spec.ts` via `testIgnore`. *Folding captures into `pnpm e2e` (couples capture to CI); a second, duplicated Playwright config (web-server drift).*

- **Feature 6: the server switches from NodeNext/`tsc`-emit to `moduleResolution: Bundler` and runs via `tsx` in both dev and production (`start` → `tsx src/index.ts`, `build` → `tsc --noEmit`)**: the chat server must consume `@openartifact/core`/`@openartifact/shared`, which are source-only packages (exports → `src/index.ts`, extensionless relative imports, bundler resolution) that NodeNext + `rootDir: src` emit cannot compile (verified TS2835/TS2305). `tsx` resolves and transpiles the source on the fly, `tsc --noEmit` still typechecks every build, and the e2e webServer runs the same `tsx` path — acceptable for a local-first, loopback-only, single-process tool. This supersedes the earlier "compiled ESM in production" decision. *Giving shared/core real `dist/` builds with `.js` extensions (prebuild ordering, dual dev/prod resolution, drift risk); a bundler build of the server (adds a bundler dependency for one process).*
- **Feature 6: the session token is issued as an httpOnly `SameSite=Strict` cookie (set by the HTML response and a `GET /api/session` bootstrap), not a URL query param**: §9 requires a random per-startup token on every request; a cookie is never echoed into history/logs and is scoped to the local origin, whereas `?token=…` leaks into the address bar and shell history. `/api/session` is token-exempt (it must be callable to *receive* the cookie), and the client calls it on load so dev (Vite-proxied) and prod behave identically. *URL query token; a `X-Session-Token` header hand-managed by the client (leaks into logs via fetch instrumentation, more client code).*
- **Feature 6: `Host`/`Origin` checks accept any loopback port (`127.0.0.1`/`localhost` on any `:port`), not just the server's own**: in dev the browser talks to the Vite proxy at `:5173`, which forwards requests to the server at `:4318`, so `Origin` arrives as `http://127.0.0.1:5173`; allowing any loopback port keeps the guard working across the dev proxy while still rejecting hostile hostnames (DNS rebinding) and foreign origins (CSRF). *Allow-listing only `:4318` (breaks dev); disabling the guard in dev (security hole).*

- **Feature 6: a second turn continues a conversation by passing `conversationId` in the `POST /api/chat` body (omitted → a fresh conversation), and the registry rejects a concurrent turn with 409 while one is in flight**: design.md fixes the endpoints but not how a follow-up turn names its conversation, and the SSE stream itself must reveal the new id before any approval/stop can target it. The chat stream therefore opens with a `conversation` event carrying the id; the client echoes it back for the next turn and for approval/stop. *A `/api/chat/:conversationId` path (conflicts with the approval/stop subroutes); deriving the id from a response header (SSE headers are awkward to read through fetch).*
- **Feature 6: the approval seam buffers a decision that arrives before the loop registers the pending approval** (`conversation.pendingDecision`): the loop yields `approval_request` *before* it calls the `ApprovalHandler`, so a very fast client can post a decision in the gap between the SSE write and the handler registering the pending promise; the handler consumes any buffered decision first, making the round-trip race-free. *Rejecting 409 "no pending approval" (races the client); pre-registering the pending promise outside the loop (would require reordering core's yield/handler sequence).*
- **Feature 6: chat SSE events are serialized as `event: <type>` + a single-line JSON `data:` body, with the event object kept in `data`** (the `event:` name mirrors it for the fetch-based parser); the wire type lives server-side in `routes/chat.ts` for now and is promoted to `packages/shared/src/chat.ts` in task 4.1, where it becomes the server↔web contract. Command output forwards as a dedicated `command_output {stream,text}` event. *SSE with empty `event:` and a `type` only inside `data` (the client must parse JSON to route); a bespoke non-JSON line protocol (more parser surface for no gain).*
- **Feature 6: a per-conversation provider factory (fake → fresh `FakeServerProvider`, real → fresh `createProviderAdapter`) instead of one shared adapter**: `FakeServerProvider` is stateful (replays turns in order), so each conversation must start its replay from turn one; real adapters are stateless but the factory keeps the wiring uniform. The factory is injectable on `createApp` (`providerFactory`) so tests can replay a single fixture turn (e.g. the slow Stop turn) in isolation. *One shared provider instance (the fake would replay turns across conversations); constructing a full `AgentRuntime` up front and cloning it (the loop owns history and cannot be cloned).*

- **Feature 6, task 5.1: the chat pane stacks vertically as messages → composer → collapsible terminal log, with the terminal log as the pane's foot**: the composer belongs directly under the conversation it is answering, and the step-5 shell already pins the terminal log to the foot (`shrink-0 border-t`), so inserting the composer between the two keeps the typing surface adjacent to the messages while the streamed command output stays at the bottom. *Composer below the terminal log (separates the composer from the conversation and puts a collapsible region under the input).*
- **Feature 6, task 5.1: message text renders as plain pre-wrapped text (no markdown) for now, and auto-scroll pins to the bottom with a 40 px threshold, re-pinning when a new user turn is appended**: markdown/artifact/mermaid parsing of assistant text is feature 7 (inline Mermaid and artifacts are its scope), so feature 6 keeps the streamed-message rendering a faithful plain-text `whitespace-pre-wrap`; the 40 px threshold absorbs sub-pixel rounding so the list does not fight the user, and appending a user message (a new send) re-pins the view even if the user had scrolled up mid-turn. *Rendering markdown now (pulls feature-7 scope forward); a zero threshold (scroll fights rounding); never re-pinning on send (a new turn can start out of view after the user scrolled up).*
- **Feature 6, task 5.1: the composer's Send icon is an authored up-arrow (`SendIcon`), the textarea grows to a 160 px cap, Enter sends and Shift+Enter inserts a newline (IME composition never sends)**: the icon stays in the authored 1.5-stroke SVG set (no new dependency), the cap keeps long drafts scrolling inside the textarea instead of pushing the conversation out of view, and guarding `event.nativeEvent.isComposing` prevents Enter from sending while a CJK IME is confirming a composition. *A paper-plane glyph (same set, but an arrow reads more literally as "send/enter" in a code tool); an unbounded autogrow (the composer can consume the whole pane); sending on Enter during IME composition (breaks CJK input).*
- **Feature 6, task 6.1: the approval card renders a line diff from a common-prefix/suffix trim (`apps/web/src/lib/diff.ts`), not a full diff library**: `edit_file` supplies the exact before/after string pair and edits are small, so a dependency-free prefix/suffix trim produces an honest, readable diff (shared head/tail become context, the changed middle splits into removed-then-added) without pulling in a diff engine for one UI surface. *A diff dependency (pinned-dep surface for a single card); showing only the raw old/new strings side by side (reads as two blocks, not a diff).*
- **Feature 6, task 6.1: the approval card shows the command's working directory as the `cwd` argument when present, else the literal label "workspace root"**: §8 requires "full command + working directory" on command approval cards, but the client does not yet know the absolute workspace root (`/api/session` returns only approval-mode/provider flags, and surfacing the root is a settings/session concern for feature 8). The `execute_command` args carry an optional relative `cwd`; rendering it (mono) or the "workspace root" fallback keeps the card honest without widening the session contract in a UI-only task. *Adding `workspaceRoot` to `/api/session` now (server + shared + a client session store, beyond task 6.1's scope); showing no working directory (fails §8).*
- **Feature 6, task 7.1: the web client's `GET /api/session` bootstrap is implemented as `apps/web/src/lib/session.ts`, awaited in `main.tsx` before the first render**: design decision 4 promised the call but no earlier task wired it, which would make every browser chat request a 401 (the token cookie is never set). Awaiting before render makes the cookie deterministically present before the UI is interactive, so e2e is race-free; the call is non-throwing (a missing/unreachable server still renders the shell and the chat request surfaces its own error). *Calling it fire-and-forget after render (racy: a fast e2e send could beat the cookie); moving the fetch into the store (session bootstrap is not store state yet).*
- **Feature 6, task 7.1: the e2e webServer sets only `OPENARTIFACT_FAKE_PROVIDER=1` — no separate workspace env var**: in fake mode the server already creates the seeded temp workspace itself (`createFakeWorkspace` in `apps/server/src/index.ts`), so `OPENARTIFACT_WORKSPACE_ROOT` would be overridden anyway and only `OPENARTIFACT_FAKE_PROVIDER=1` is needed for a key-free, network-free run. *Setting a fixed workspace root (overridden by the fake workspace; risks collisions); passing a per-run temp path into Playwright (the server owns the workspace lifecycle).*

- **Feature 7: the incremental `StreamParser` moves from `packages/core` to `packages/shared` (core re-exports it)**: the web must parse `<artifact>` blocks and ```mermaid fences from assistant text (§6) but may never import `packages/core` (it pulls `node:*` through tools/providers/agent and breaks the Vite build), while the parser itself is already pure (only zod, no DOM/node). One parser in `shared` serves both sides and keeps the fuzz-verified state machine single-sourced; `packages/core/src/parser/` becomes a re-export so `providers/fallback.ts`, `prompts/system.ts` and the existing tests keep their imports. *A web-only re-implementation (drifts from a fuzz-tested state machine); a new `packages/parser` leaf package (a third package for two files).*
- **Feature 7: only the iframe's dependencies go through `/vendor` (CORS); the app's own runtime deps are Vite-bundled and dynamic-imported**: `react`/`react-dom`/`lucide-react`/`recharts`/`@tailwindcss/browser` run inside the opaque-origin sandbox iframe, so they are esbuild-bundled once into `apps/web/public/vendor/` and served by a server route with `Access-Control-Allow-Origin: *`. `mermaid`, `dompurify`, `shiki` and `sucrase` run in the parent app (SVG/Mermaid/Code render inline in the panel; sucrase transpiles React source in the parent before writing the srcdoc), so the app imports them normally and Vite code-splits them via dynamic `import()` — no vendor file, no CORS, no CDN. *Vendoring every runtime dep (larger vendor surface, duplicated mermaid/shiki); fetching anything at runtime (breaks offline).*
- **Feature 7: React artifacts transpile in the browser with `sucrase` (automatic JSX runtime) rather than `esbuild-wasm`**: sucrase is pure JS and small, and the import map (not the transpiler) resolves the four vendored imports; esbuild-wasm adds a multi-MB wasm payload for the same TSX→ESM transform. The import map pins `react`, `react-dom`, `react/jsx-runtime`, `lucide-react` and `recharts` so an unknown import fails loudly through the error bridge instead of a blank screen. *esbuild-wasm; a hosted bundler (Sandpack) which sends user code off-machine and breaks offline (explicitly rejected by §6).*
- **Feature 7: the client parses the accumulated assistant text in "whole document" mode on every render (`push(full)` + `end()`) rather than incrementally across deltas**: the `StreamParser` is incremental, but the fuzz test already proves whole-input equals any split, so re-parsing the growing message content per render is correct and idempotent, and content is bounded by the context cap (~20k chars) so the per-render cost is negligible. A `parseDocument(content)` reducer folds the event sequence into text blocks, inline Mermaid blocks, and artifacts keyed by identifier with a `versions` list. *Maintaining a long-lived incremental parser instance per message (re-entrancy/ordering complexity across re-renders for no benefit).*
- **Feature 7: the artifact model stores a `versions` list but renders only the latest; version dropdown, diff, revert and "Write to disk" are deferred to feature 8**: §12.7's acceptance criteria (render all five types, sandbox isolation, inline Mermaid error, themed diagrams) do not exercise version diff/revert (§12.8) or write-to-disk, and both write-to-disk and "Undo this turn" need a user-initiated tool execution + approval seam outside the agent loop — the same new server machinery, so they land together in feature 8. Establishing the `versions` array now (a reused identifier appends, an in-progress version updates in place, never replacing history) gives feature 8 the model to hang the dropdown and Monaco diff on. *Deferring the version model entirely (feature 8 would then rework the store); adding write-to-disk in feature 7 (a half-finished server mutation without the undo/snapshot support it pairs with).*
- **Feature 7, task 1.1: the parser's `TextEvent` is renamed to `ParserTextEvent` when the parser moves into `packages/shared`**: `shared/src/chat.ts` already exports a `TextEvent` (the chat wire event `{type:"text", text}`), so `export * from "./parser"` next to `export * from "./chat"` in `shared/src/index.ts` triggered TS2308 (ambiguous re-export of `TextEvent`). The parser event and the chat event are different unions, so the parser type gets an unambiguous name (only `TextEvent` collides; the other parser events are unique). `stream-parser.ts`, the tests and `fallback.ts` never name `TextEvent` directly (they use `ParserEvent`/`Extract`), so the rename touches only the three re-export/definition files. *Keeping `TextEvent` and dropping `export * from "./parser"` in favour of a curated re-export list (the web and core need the parser types by their original names); renaming the chat `TextEvent` instead (that one is the wire contract already shipped in feature 6).*
